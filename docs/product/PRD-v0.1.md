# HealthThread｜AI 个人健康管家
## 产品需求文档 PRD v0.1

**从一次身体不适开始，持续记录、准确接续。**

基于 Agnes Harness 的个人健康管理 Agent，以可追溯、可纠正的健康记录为基础，连接日常记录、就诊准备与科室参考、诊后资料更新和医嘱事项跟进。就诊是服务节点，不是开始使用的前提。

| 日常记录 | 就诊准备 | 诊后接续 |
| --- | --- | --- |
| 文字／语音转文字；保存原文并整理候选事实 | 复用相关历史与当前表达；科室参考、表达稿和问题清单 | 上传病历；核对差异、更新画像、跟进医嘱事项 |

## 01 产品目标、用户与 MVP 范围

### 1.1 产品目标与问题定义

用户平时难以持续整理身体不适；准备就诊时需要重新回忆经过；诊后材料与此前记录又可能分散。产品要让“这次说的事”接得上“以前说过的事”，并可查看来源、纠正错误、更新后续产物。以上为本项目的问题假设，不代表已完成用户研究。[S1 §01—§02；C1]

拟验证三个结果：记录少重复填写；诊前表达少遗漏和时间混淆；诊后新增信息能准确回到个人记录。首期成年人、合成数据、本地演示是框架建议，目标人群与真实试用安排仍待团队确认。

### 1.2 范围基线

| 功能 | 本期交付边界 | 优先级／状态 |
| --- | --- | --- |
| F01 日常记录 | 文字、发生时间、原文、记录列表；提取失败不丢原文 | P0／沿用 |
| F02 语音转文字 | 录音、真实转写、编辑校对；许可与能力需验证 | P0 条件项／沿用 |
| F03 健康画像 | 结构化事实、来源、状态、时间线、关联与纠错 | P0／沿用 |
| F04 就诊准备与导医 | 当前主诉＋历史；仅科室参考；表达稿、问题清单、沟通卡 | P0；依据路径存在 D01 |
| F04-05 就医／观察提示 | 修改稿提出的候选能力；不能补造阈值、观察时长或排除急症结论 | 优先级与规则待 D02 |
| F05 病历上传与更新 | 文字材料、可提取文本的 PDF；来源对照、差异确认 | P0／沿用 |
| F06 诊后恢复支持 | 已确认医嘱的解释、生活注意事项、待询问及复诊事项 | P0／沿用 |
| F07 数据权利与安全 | 授权、来源、隔离、删除、导出、脱敏运行证据 | P0／沿用 |
| F08 体验扩展 | 扫描／手写识别、主动提醒、更多格式；更多科室覆盖待 D01 | P1／沿用并标冲突 |

### 1.3 不纳入本期

不自动诊断、开药、停药或调整剂量；不作疾病概率、全身健康总分或康复保证。不推荐具体医院和医生，不接挂号交易、医院信息系统和可穿戴设备，不训练医疗模型。三维人体、数字人、原生 App 不是本次已确认需求，不因“视觉效果”一词自动加入。

**产品完成不等于医疗效果成立。** 本期证明记录、来源、纠错和跨阶段接续可靠；真实试用仍受框架中的独立放行条件限制。[S1 §01、§10]

## 02 用户旅程与闭环交付

### 2.1 五阶段旅程

| 阶段 | 用户目标与主要行为 | 系统交付／完成标志 |
| --- | --- | --- |
| A 日常记录 | 用自然语言记录当前不适；必要时补时间或核对 | 原文已保存；候选事实有来源；可稍后确认；模型失败不丢记录 |
| B 准备就诊 | 说明目前最困扰的问题，选取相关历史 | 当前主诉、相关病程、缺失／冲突提示、科室参考；未决能力状态可见 |
| C 医生沟通 | 修改表达稿，查看想问的问题，复制或打印 | 一分钟表达稿、问题清单、来源；沟通卡是否独立一页按 D06 |
| D 诊后上传 | 上传病历，对照原文确认新增、变化和冲突 | 原件索引、待确认变更；确认后得到新版本，不静默覆盖 |
| E 恢复接续 | 查看医嘱事项，记录完成／暂停或新的身体变化 | 有来源的事项；新变化重新进入 F01/F03，保留前后关联 |

日常功能独立可用；用户没有就诊，也能记录、查询和纠错。不把去医院、上传病历或填写完整档案设置为首次使用前置条件。[S1 §01—§02]

### 2.2 用户故事（建议细化）

| 编号 | 用户故事 | 关联功能 |
| --- | --- | --- |
| US01 | 我只想先说现在不舒服的地方，不愿先填完一张健康调查表 | F01、F02、F03 |
| US02 | 我发现日期记错，希望改正后后续材料也用新日期 | F03、F04、F06 |
| US03 | 我准备就诊，希望不用从头回忆每一次变化 | F04 |
| US04 | 我拿到病历，希望系统说明“提取了什么、准备更新什么”，由我核对 | F05、F03 |
| US05 | 我希望看懂已有医嘱，并把下一次变化继续记录下来 | F06、F01 |
| US06 | 我希望知道信息来自哪里、发给谁处理，并能导出或删除 | F07 |

### 2.3 唯一主演示故事

沿用框架中的合成用户：两条不适记录 → 更正首次出现日期 → 生成引用新日期的就诊材料 → 上传模拟病历 → 核对差异 → 查看基于该病历的事项 → 再次记录变化。[S1 §2.2]

建议额外插入一次“关闭并重新打开会话”，检查历史能否从业务存储恢复，而不是依赖同一聊天窗口。具体症状主题、合成病历、期望字段和允许输出，由团队在 D10 中登记，不用成员真实健康资料替代。

## 03 信息架构、页面与视觉要求

### 3.1 视觉与导航基线

六个逻辑页面沿用原编号。是否合并路由、移动端是否折叠菜单，是建议设计议题，不是已经批准的导航实现。建议保留“刚记录的内容、正在处理的状态、待核对事项”的清晰层级，避免首页只剩一个无状态聊天框。

| 页面 | 主要内容与操作 | 关键状态／跳转 |
| --- | --- | --- |
| P01 记录首页 | 文字与语音入口、最近记录、时间补充、待核对提示 | 空档案；原文已保存但分析中；转写失败；进入 P02/P03 |
| P02 健康时间线 | 按问题／时间筛选；查看原文、来源、版本；更正及标记变化 | 当前／历史／待确认／冲突／无匹配；可进入就诊准备 |

| P04 沟通卡 | 表达稿、结构化摘要、问题清单、编辑、来源、复制与打印出口 | 草稿／已确认／已过期；独立一页形式待 D06 |
| P05 病历与恢复 | 上传、原文对照、字段校对、差异确认、医嘱事项与反馈 | 解析中／部分识别／需校对／上传失败／事项停用；反馈返回 P01 |

### 3.2 页面操作的一致性（建议细化）

关键按钮描述具体行为：“保存记录”“确认本次变更”“重新生成材料”，而不是用同一个“确定”覆盖所有动作。保存、模型处理、用户核对、提交成功分开显示；不把文件上传成功写成画像更新成功。

就诊材料应显示生成时间和所用资料版本。来源更新后先提示过期；是否自动重生成在 D06 中确定。首页侧栏入口可先按上述功能组织，最后由 A 交付可点击原型，B/C 确认可实现状态。

### 3.3 视觉组件、信息语义与交付

| 组件／效果 | 交付要求 | 不应出现的表现 |
| --- | --- | --- |
| SourceBadge 来源 | 区分用户自述、上传材料和模型整理；点击可定位依据 | 用“已确认”暗示医学判断已由医生确认 |
| FactDiff 变更对照 | 新值、旧值、来源、确认选择；冲突可暂不提交 | 不展示差异就把新病历覆盖旧画像 |

| SafetyNotice 提示 | 与普通状态区分；文字可读、原因与下一步明确 | 只靠红绿颜色；用绿色表示“已排除危险” |
| 沟通卡／事项卡 | 区分原文、解释和待询问；兼顾长内容和来源 | 将模型补写内容排版为医生原始医嘱 |
| 健康时间线 | 发生时间、记录时间、当前／历史和纠错关系可理解 | 把补录时间当发病时间；缓解后消除历史 |
| 可选人体图／趋势图 | 是否实现由 D05 决定；采用时必须来自明确字段 | 为视觉效果新造风险热力图、疾病概率或健康总分 |

### 3.4 可视化数据规则

沿用框架：未知数值不画成零；主观程度仅展示用户实际填写的数值，并标“用户自评”；趋势只比较相同指标、单位与明确时间范围。不将“有点不舒服”转换为评分，不把资料完整度当作健康程度。[S1 §04]

建议同时展示空、加载、失败、待核对、冲突与已过期状态。任何可选动效都不应阻断输入、查看来源和确认；静态降级形式由 A 在设计交付中说明。

### 3.5 A 的视觉交付与运行版验收（建议细化）

A 交付六页原型、公共组件与状态表、白绿主题规范、图标／资产、交互与可选动效说明；B/C 将它们接到实际流程。采用哪个设计工具、A 是否提交组件代码，均待 D07，不假设视觉职责等于全部前端工程。

验收检查：同一事实在多个页面的状态一致；来源和冲突可找到；长表达稿和空数据不遮挡操作；桌面与手机目标尺寸可完成主流程；键盘可操作关键控件。设备清单和视觉容差由团队填写，不预设未经同意的性能或像素指标。

## 04 功能需求详单

### F01 日常文字记录

**优先级：P0。** 关联 P01/P02、W1、API01/API03/API04/API10；建议主责 B，候选提取由 C 配合。来源：[S1 §01—§05、§07—§09；C1、C3]。

**用户目标：** 先留下当前不适，再逐步完善资料；不等待症状结束，也不要求先建完整档案。以下规则与验收为对来源要求的建议细化。

| 子需求 | 用户输入／系统行为 | 可检查的输出 |
| --- | --- | --- |
| F01-01 记录采集 | 接收用户原话、可选发生时间及输入来源；空值和模糊时间保留其含义 | 原始记录、服务端记录时间和记录编号 |
| F01-02 先存后分析 | 在持久保存成功后才反馈“已保存”；再启动提取任务 | entry_id、run_id；保存与分析状态分离 |
| F01-03 候选提取 | 提取表现、时间、部位等；复用相关背景；只追问当前必要缺口 | 候选事实、来源、缺失或冲突提示 |
| F01-04 继续与补录 | 新变化新增记录；明显更正转 F03；事件关联不确定时不强行合并 | 新记录及可追溯关联；不会覆盖原话 |
| F01-05 失败恢复 | 保存成功、分析失败时保留原文；网络保存失败时不得显示已保存 | 可区分的错误、重试入口与已有结果状态 |

**输入与输出约束：** 模型只能提出候选；原话中未提到的情况不写成否定。普通记录可按授权保存为“未确认自述”；重要字段与冲突按 F03 核对。最大字数与关联判断标准留在 D09/D11。

**主流程：** 输入 → 保存原文 → 显示已保存／分析中 → 整理候选 → 必要核对 → 时间线可见。

**异常路径：** 未授权则说明所需授权；空输入不启动任务；模型超时不丢原文；结果格式失败按工作流预算处理。重试沿用已有记录，不重复创建同一条输入。

**验收 AC-F01：** 提交一条带模糊时间的合成记录，能查看原话和来源；人为使分析失败，原文仍在；再次处理不会多出重复输入；用户未填写程度时，结构化结果和界面都不出现自动分数。

**待确认：** 输入上限、草稿保留策略、每轮补问数量、普通候选的自动归档授权范围。

### F02 语音转文字

**优先级：P0 条件项。** 关联 P01、W1、API02/API01/API10；建议 B 负责录音／校对入口，C 负责能力验证和转写适配，A 负责状态设计。来源：[S1 §01、§03、§10、§14；C1]。

**用户目标：** 能够用说话代替打字，但在保存为自己的表达前可以检查转写。语音路线没有许可与实际调用证据时，不得视为已完成。

| 子需求 | 用户输入／系统行为 | 可检查的输出 |
| --- | --- | --- |
| F02-01 授权与录音 | 告知处理去向与保存策略；用户允许后开始，可停止或取消 | 明确录音状态；取消不伪装为转写成功 |
| F02-02 转写 | 经已确认允许的真实能力处理音频；不把粘贴文本冒充识别 | transcript、处理状态、输入来源 |
| F02-03 校对 | 转写可编辑；时间、数字、否定、药名等内容提示核对 | 校对后的文本；区分自动转写和用户改动 |
| F02-04 提交 | 用户确认文本后复用 F01 的保存与提取流程 | 与文字记录一致的 entry_id、来源和后续状态 |
| F02-05 不可用时降级 | 权限拒绝、无声、超时或能力未启用时明确报错 | 保留文字输入；标明语音能力未完成／不可用 |

**原始音频策略：** 框架建议默认不长期保存；具体保存、删除时点和第三方保留说明需要 D08/D11 决定。校对后的文本仍是用户自述，不因来自语音而成为医学确认信息。

**主流程：** 授权 → 录音 → 停止 → 转写 → 编辑／核对 → 提交 → 进入 F01。

**验收 AC-F02：** 完成一次真实录音转写并修改日期后提交，后续事实使用校对值；拒绝麦克风或转写失败时仍可打字；取消录音不会新增健康事实；公开演示清楚区分真实转写和文字降级。

**条件交付记录：** 能力提供方：［待填写］；赛事适用性记录：［待填写］；实测日期：［待填写］；支持终端：［待填写］；完成／未完成及限制：［待填写］。

在条件未成立时，保留需求但如实记录未完成；文字闭环不得因此阻塞。不得擅自接入框架未获许可的第三方模型路径。

### F03 健康画像、时间线与纠错

**优先级：P0。** 关联 P02及各来源／差异组件、W1/W3、API03/API04/API05；建议主责 B，C 提供候选与关联依据。来源：[S1 §04—§05、§09、§13；C3]。

**用户目标：** 知道系统记住了什么、依据是什么，以及怎样纠正。画像是记录视图，不是模型自由生成的综合健康判断。

| 子需求 | 规则 | 输出／状态 |
| --- | --- | --- |
| F03-01 四类视图 | 当前关注、事件时间线、相关已确认背景、冲突与未知 | 同一数据来源支持多个视图 |
| F03-02 来源查看 | 从事实定位原文、资料及其日期；区分自述与病历 | source_id、原文定位、review_status |
| F03-03 候选确认 | 关键更新先对照；允许暂不确认；冲突不自动覆盖 | 待核对／确认／有冲突；提交回执 |
| F03-04 事实更正 | 更正建立新版本和替代关系，不改写原始出处 | 新版本、旧版本、原因；相关产物过期 |
| F03-05 身体状态变化 | 缓解或结束来自明确反馈，新增时间变化，不删除过去 | 用户自述变化及有效时间 |
| F03-06 跨会话接续 | 重新打开后从存储获取有效事实，不依赖旧聊天仍在上下文 | 记录、版本与关联产物一致 |

**关联规则：** 同一身体部位不自动等于同一问题；没有依据时保留独立记录或待核对关联。发生时间与记录时间分开；“未记录”“明确否认”“已经缓解”分开。具体关联阈值不在本稿虚构。

**并发与确认：** 提交包含 expected_version；版本不一致时显示冲突并重新获取资料。确认意味着提取符合原话／材料，不意味着诊断正确。[S1 §04—§05、§09]

**验收 AC-F03：** 两条记录关联到一个已确认问题后，更正首次日期；时间线显示新值，原始记录仍可查看；旧沟通卡标记过期，新卡使用新值。随后记录“有所缓解”，历史不删除。重新打开会话仍保持上述结果。

**待确认：** 最小字段集合、候选确认粒度、关联策略、是否实现人体图／趋势图、产物是否自动重生成。此处不增加健康评分系统。

### F04A 就诊准备与科室参考

**优先级：F04 为 P0；F04-05 的分级待确认。** 关联 P03/P04、W2、API06/API10；建议主责 C，B 提供受限历史检索。来源：[S1 §02、§07—§10；C1]。

**修改稿新增边界：** 只做科室推荐，不做具体医院和医生推荐，科室由 AI 生成。[S1 §07，p.11]

| 子需求 | 用户行为与产品规则 | 输出／验收重点 |
| --- | --- | --- |
| F04-01 当前主诉 | 用户说明目前最困扰的问题，可补充变化和问题 | 当前主诉与历史描述分开 |
| F04-02 历史取用 | 查询当前用户的相关问题、时间范围和必要背景；允许核对纳入内容 | 有来源、版本的相关记录集合；无匹配不编造 |
| F04-03 科室参考 | 模型生成科室层面的参考与解释；具体依据、范围和校验方法依 D01 | 不包含医院、医生、排班、余号或交易信息 |
| F04-04 未覆盖／失败 | 资料不足、冲突、安全模块失败或超出支持范围时不强行给确定结果 | 缺失提示、待处理状态、人工导医路径 |
| F04-05 就医／观察提示 | 修改稿新增意图；表达语义、临床规则和范围尚未给出 | 不补观察时长或紧急阈值；验收定义待 D02 |

**核心未决 D01：** 修改稿删除意向指向 lookup_care_directory，但其 W2、API06 和安全章节仍保留“核验目录”。本稿不把查询目录当作默认必做，也不把无依据自由推荐当作确定方案。临床来源与个人历史来源是两种不同证据，不能只引用用户症状就宣称科室选择已得到医学验证。

**就医／观察发布边界：** 保留这一候选需求，不用免责声明替代规则。沿用框架 §10：未经适当审阅，只用合成案例演示相关状态，不对真实用户开放自动分级处置，不宣称已排除危险。D02 决定前不得输出“可以安全等待”等确定结论。

**验收 AC-F04A：** 历史更正进入当前准备结果；没有相关历史时如实提示；科室输出不出现医院／医生推荐；模型失败或资料不足不返回“无风险”。科室推荐质量与观察提示的实质标准，必须待 D01/D02 定稿后补充，不用“文字已生成”替代验收。

### F04B 表达稿、问题清单与沟通卡

**优先级：沿用 F04。** 关联 P04、W2、API06及结果读取；建议主责 C，A 主责内容层级和版式。来源：[S1 §02—§03、§05、§09]。

**用户目标：** 能在就诊时按事实清楚表达经过，知道还有哪些问题需要问。系统不教用户暗示某个确诊结果，也不把来源中的不确定描述改成确定判断。

| F04-07 问题清单 | 纳入用户最想问的问题和材料尚不清楚的事项 | 可编辑问题列表，不冒充医生答案 |
| F04-08 结构化承载 | 原 P04 仍保留结构化摘要和沟通卡 | 显示主诉、经过、背景、问题、未确认项与来源 |
| F04-09 用户确认 | 可查看和修改；涉及事实更正时转入事实变更流程 | 区分表达编辑和事实更新，避免形成两份不同档案 |
| F04-10 复制／打印 | 框架仍写复制与浏览器打印；独立一页形式待 D06 | 不截断关键文字；输出含生成时间及资料状态 |
| F04-11 过期处理 | 引用事实被更正后，旧卡标记 stale | 提示重新生成／导出；不宣称已撤回外部旧副本 |

**来源区分：** 用户自述、病历记载、系统整理与待询问项分别呈现。相关已确认用药／过敏背景只在确有记录且任务需要时载入，不从未提到推导“无”。[S1 §2.1、§05]

**呈现冲突 D06：** 阶段表删除了“一页沟通卡”字样，而 P04 和后续段落仍保留卡片与打印。本稿不擅自删除这些出口，但其版式与最终交付形态需团队确认。

**验收 AC-F04B：** 给定含模糊日期、否定句和一次日期更正的材料，稿件忠于有效版本，能定位来源，不加入新症状或诊断；编辑语句不悄悄改画像；事实修改经过确认后使旧卡过期。若确认保留打印出口，则长文本与来源说明均须可读。

**完成标志：** 有可查看、可核对、可使用的产物；生成了一条聊天回答或只弹出“已完成”不算交付。

### F05 病历上传、解析与画像更新

**优先级：P0。** 关联 P05/P02、W3、API07/API05/API10；建议 C 主责诊后流程，B 提供文件、权限与版本提交。来源：[S1 §01—§02、§05、§07—§10]。

**用户目标：** 上传资料后看懂系统提取了什么，以及哪些内容会更新自己的记录。材料上传不等于真实性已验证，也不等于所有字段已确认。

| 子需求 | 行为与规则 | 输出／状态 |
| --- | --- | --- |
| F05-01 文件接收 | 本期支持文字材料及可提取文本的 PDF；检查归属、授权、类型和大小 | document_id、原件引用、run_id |
| F05-02 原文提取 | 保存材料与可核对文本；扫描／手写不假装已识别 | 可查看原文；无文本／不支持／部分提取状态 |
| F05-03 信息整理 | 提取诊断记载、检查、医嘱和安排，逐字段关联出处 | 带来源的候选；保留“考虑／待排”等词 |
| F05-04 差异核对 | 对比已有事实，将新增、变化、冲突和不清楚内容分开 | 原文与旧值／新值对照；用户可暂缓 |
| F05-05 受控提交 | 关键字段确认后由后端校验并提交，验证目标版本 | 画像新版本及回执；关联产物失效 |
| F05-06 接到诊后事项 | 仅将已确认来源送入 F06；无法识别内容保留待咨询 | 医嘱事项入口和未解决提示 |

**错误路径：** 加密或无可提取文本、超大文件、解析超时、无效模型输出、版本冲突均需可区分。实际支持扩展名、大小、加密处理路线未给出，留在 D08；不把全部扫描识别提前升级为 P0。

**更新规则：** 旧病历和新自述不同不一定是错误，可能是不同时间的状态。新材料不能无条件覆盖旧记录；没有明确依据时，不自动把“曾使用”变成“正在使用”。重要字段核对规则与 F03 共用。

**验收 AC-F05：** 用可提取文本的合成病历完成上传、提取、原文定位、差异核对和更新；未确认前画像不出现已确认的新诊断；含“待排”的内容仍保留不确定性；无文本 PDF 返回限制说明而不是编造结果；重复提交不重复更新。

### F06 医嘱事项与诊后恢复支持

**优先级：P0。** 关联 P05/P01、W3、API08/API09；建议主责 C，B 保证新反馈回到记录与版本系统。来源：[S1 §01—§02、§05、§07、§10；C1]。

**用户目标：** 理解已经获得的医嘱，明确还需问什么，并在日常生活中继续记录变化。这里的“恢复支持”不等于系统另开治疗方案。

| 子需求 | 内容与交互规则 | 产物 |
| --- | --- | --- |
| F06-01 事项生成 | 从已核对的医嘱和安排中提取事项，不补不存在的要求 | instruction_source、原文、解释、日期及状态 |
| F06-02 类型区分 | 原始医嘱、通俗解释、一般资料、待咨询项分开 | 每张卡显示类型和来源；不能混排成医生原话 |
| F06-03 生活注意事项 | 先解释材料已有内容；一般资料需有可查来源，材料不足就待咨询 | 不凭空添加饮食、运动、剂量或禁忌 |
| F06-04 状态与反馈 | 用户可完成／暂停事项；身体新变化作为新记录进入 F01 | task_id 与新 entry_id／episode 的关联 |
| F06-05 资料更新 | 来源更正后相关事项需重新核验或提示过期 | 不继续执行可能已失效的说明 |
| F06-06 提醒边界 | 本期显示已记录的复诊／待办；主动推送属于 F08 | 不把页面待办宣称为已设置且可靠送达的通知 |

**事项状态与健康状态分离：** 完成一张事项卡不代表疾病康复；暂停事项不等于医生已取消医嘱。新病历或反馈如何改变事项，应由来源、确认和版本规则决定，而不是按沉默或长期未登录自动推断。

**安全边界：** 不开药、停药、改剂量；不保证康复；资料不清楚时列待咨询，疑似紧急情况进入框架规定的异常路径。未获适当审阅前，真实使用范围仍受限制。[S1 §10]

**验收 AC-F06：** 合成病历只有一条明确安排时，不新增无出处的疗法；每条事项可回到对应原文；含糊日期保留待核对，不补造具体日期；用户提交新变化后，能在时间线看到该记录并继续用于下一次就诊准备。

**待确认：** 事项分类、一般资料来源、日期核对方式和是否保留用户自建事项；后者不是本稿新增的默认能力。

### F07 数据权利、安全与可追溯性

**优先级：P0。** 关联全页面与 P06、API11及授权接口；建议主责 B，A 负责用户可理解的交互，C 负责模型／运行范围约束。来源：[S1 §05、§07、§09—§10]。

| 子需求 | 产品规则 | 验收要点 |
| --- | --- | --- |
| F07-01 告知与授权 | 输入、语音、上传及模型传输前说明目的、内容、去向和期限 | 授权状态与实际处理一致，未授权不启动对应处理 |
| F07-02 数据归属 | 服务端确定当前用户，记录／工具访问校验归属 | 使用另一个用户的编号不能读取或修改数据 |
| F07-03 导出 | 明确导出范围；保留原话／整理结果、来源和确认状态差别 | 导出的内容与所选有效版本一致；格式待 D11 |
| F07-04 删除 | 展示原件、事实、索引、派生物及适用轨迹的处理范围 | 有处理结果；部分未完成如实显示，不只从页面隐藏 |
| F07-05 撤回与取消 | 撤回阻止对应后续处理；取消任务说明已完成的效果 | 不把“已取消”显示为“所有写入都已撤销” |
| F07-06 证据输出 | 开发和公开演示默认合成材料；运行证据脱敏 | 不含密钥、真实个人资料或未经检查的完整 Home |

删除与纠错不同：日常更正保留版本，不代表用户删除请求后必须永久保留敏感原文。保留期限、第三方处理、备份清理与导出格式依 D11；本稿不编造“立即完全删除”的保证。

**验收 AC-F07：** 两套合成用户数据隔离；撤回后新任务被阻止；删除任务能列出完成／未完成范围；导出与当前状态一致；证据包不能包含真实敏感数据。真实试用另需满足框架 §10.3 的条件。

### F08 后续体验扩展

**优先级：P1，不阻塞本次基础闭环。** 沿用扫描／手写识别、主动提醒、更多资料格式等范围。更多科室覆盖依 D01，不能解释成恢复医院与医生推荐。

扩展进入开发前，需填写用户价值、依赖能力、处理来源、失败路径、测试和资源成本。三维人体、数字人、主动提醒、向量数据库均不因“有助展示”自动进入本期。取消扩展不能删去 P0 的来源、纠错和权限验收。

## 05 健康数据、记录维护与长期记忆

### 5.1 结构化范式：问题事件＋时间＋证据

沿用框架定义，这是信息组织草案，不是医学量表、诊断模型或健康评分标准。模型提取只是候选；量化来自用户明确给出的数值或材料，不能根据自然语言强行换算。[S1 §04]

| 维度 | 最小表达内容 | 规则 |
| --- | --- | --- |
| 部位与表现 | body_site、symptom、左右侧、原话和标签 | 原话与标准化标签并存，不从症状直接生成疾病事实 |
| 时间与变化 | onset、course、持续／频率、有效时间 | 发生时间与记录时间分开；模糊时间保留原文或区间 |
| 主观程度 | self_rating；可选用户自评数值 | 未提供为 null；不作为急重分级或全身健康分数 |
| 影响与情境 | impact、context；生活影响、诱发／缓解描述 | 只整理表达过的内容；相关不改写为因果 |
| 伴随与否定 | associated、polarity、否定作用范围及时间 | 未提到不等于没有；过去否认不自动代表当前否认 |
| 测量与资料 | value、unit、测量日期、资料范围 | 数值不丢单位；参考范围必须有相应依据 |
| 背景与处理 | medication、history、已确认相关过敏／用药 | 曾有与当前分开；不自动推断使用变化 |
| 证据与状态 | source、原文定位、review、revision、有效状态 | 未确认不升级为确诊，上传件不等于已验真 |

### 5.2 数据对象与产品职责

| 对象 | 主要职责 |
| --- | --- |
| 原始记录／文档 | 保存实际输入与材料及来源身份；不能被模型摘要替代 |
| 健康事实与版本 | 保存候选、有效值、确认状态、原文依据、替代关系和更正原因 |
| 问题事件 | 关联多次记录；关联依据不充分时保留不确定 |
| 画像与时间线 | 从事实组织的视图，不是独立且自由改写的真相来源 |
| 就诊材料／健康摘要 | 保存引用的 fact_id＋revision；依赖变化后可标记过期并重建 |
| 医嘱事项／运行记录 | 事项关联原文；运行关联任务、用户、结果与真实工具回执 |

用户授权、记录归属与删除范围仍须实现；上表不是可以省略这些对象的数据库建表清单。物理表结构交技术文档确定。

<!-- pagebreak -->

### 5.3 “维护记录”不是每次生成一个 MD

框架明确将业务数据库作为事实存储；对话进一步讨论了“存储—上下文—文档”的不同职责。本 PRD 据此规定产品行为：用户每次补充信息即可保存，不等事件结束；需要执行任务时读取相关资料；文档是可选摘要或导出产物。[S1 §05；C3]

| 环节 | 建议实现职责 | 不应混淆为 |
| --- | --- | --- |
| 保存 | 原文、来源、时间、候选事实和版本进入受控存储 | 仅存在模型上下文或一个临时聊天窗口 |
| 理解 | AI 提取候选、提出关联或更新建议 | AI 获得无限制改写全部档案的权限 |
| 提交 | 后端校验结构、来源、权限和版本，必要时核对后提交 | 模型回复“已更新”就算写入成功 |
| 使用 | 从外部查询当前任务所需记录，再装入上下文 | 每次把所有用户资料全部发送给模型 |
| 展示／导出 | 生成健康摘要、沟通卡等，标明版本与来源 | 用摘要反复覆盖原始依据 |

### 5.4 四种操作分开处理

**新增记录：** 一次新的描述或反馈，保留独立输入与时间；可以属于已有问题。

**新状态变化：** “今天较前缓解”增加新的状态事实，不能删除先前的不适。

**更正旧信息：** “开始日期说错了”形成更正关系和新版本；相关旧沟通卡／事项失效或待核验，不静默沿用。

**删除：** 按用户请求处理原件、事实、索引、缓存、派生物和适用轨迹；不能以“需要追溯”为由忽略删除范围。

以上操作语义沿用框架，具体字段、事务和产物刷新策略为技术待定项。原始输入模型提取失败也要保留；写入回执未知时先查状态，不能盲目重复提交。

### 5.5 事实核对的低打扰原则

普通候选可以按明确授权先归档为未确认自述；重要药名／剂量、过敏、诊断记载和冲突更新需重点核对。不要求每次确认所有字段，也不把“减少打扰”解释成静默确认。用户能从后续页面回到原文和更正入口。[S1 §3.2、§5.1]

<!-- pagebreak -->

### 5.6 RAG／检索与上下文组装

**来源现状：** §05 新增“RAG 索引”，但 §5.3 仍规定 user_id＋问题关联＋时间范围＋关键词的最小检索，并暂不引入向量数据库、额外嵌入模型或知识图谱。本 PRD 不将“RAG”自动翻译成必须先生成 MD、分块和向量化。[S1 §05，p.8]

**确定的产品结果：** 在当前授权用户范围内，找到相关且版本有效的资料，让模型能引用它；可知道检索到了什么、没找到什么。是否增加索引及其类型，由 D03 决定。

| 任务 | 需要装入的资料（建议细化） | 必须避免 |
| --- | --- | --- |
| W1 日常记录 | 当前输入、可能相关的问题记录、必要已确认背景、待核对项 | 将同一部位直接判为同一疾病或问题 |
| W2 就诊准备 | 当前主诉、相关病程、有效更正、必要背景、用户问题 | 旧版本替代新版本；检索不到就写“从未发生” |
| W3 病历更新 | 当前资料原文、需比较的旧事实、已知冲突 | 新上传件无条件压过全部历史 |
| 诊后事项解释 | 已确认医嘱、事项状态及相关新反馈 | 仅凭摘要补写医嘱、剂量或禁忌 |

### 5.7 检索产物的最低字段

建议返回记录／事实编号、所属问题、事实值、有效时间、来源类型、原文定位、确认状态和版本。无匹配返回明确空结果；检索失败与没有历史分开。结果必须限制用户范围，必要的相关背景单独按已确定规则取用，不能只靠文本相似度假定医学重要性。

### 5.8 摘要与缓存

健康摘要或 MD 导出可以保留，但必须能回到事实与来源，标明生成时间和使用版本；更正或删除后处理其过期与重建。模型生成内容不能作为新的独立病历证据回流。缓存刷新和索引更新的具体方式留给技术方案，不在 PRD 中假定已经支持。

**验收重点：** 更正后重开会话仍使用新事实；删除后不从旧索引取回内容；故障时不声称“没有历史”；跨用户不能检索。关键测试对应 T02、T07、T08 与新增建议 T11。

## 06 Agent 工作流与执行约束

沿用框架：一个主要 Agent、三条受控工作流；Agnes 理解与草拟，程序负责权限、来源、校验和受控写入。AGH 负责实际执行记录，不用模型编写的日志冒充工具证据。[S1 §08]

| 工作流 | 拟保留步骤 | 产物／未决点 |
| --- | --- | --- |
| W1 日常记录 | 保存输入后解析 → 查询背景 → 提取候选 → 检查缺失／冲突 → 必要核对 → 后端提交 | 候选／事实版本；失败不丢原文 |
| W2 就诊准备 | 检查允许范围与安全状态 → 检索历史 → 确认主诉 → 生成科室参考 → 生成表达稿／问题清单 → 校验 | D01 决定科室依据与是否还需目录步骤；D02 决定就医／观察分支 |
| W3 诊后更新 | 提取资料 → 字段关联原文 → 对比旧事实 → 用户核对 → 后端提交 → 整理并校验事项 | 画像新版本、来源与事项；不清楚内容进入待咨询 |

### 6.1 工具与批注的处理

| 名称／能力 | 当前处理 |
| --- | --- |
| retrieve_health_context | 保留受限检索能力；项目自定义工具，不是 AGH 已有健康能力 |
| extract_document_text | 保留受限文本提取；不执行文件里的指令或链接命令 |
| lookup_care_directory | 修改稿明写“//不需要”；不列入默认必做，其他旧依赖交 D01 |
| validate_fact_patch / validate_output | 尾部“//”含义不清；校验仍是正文要求，工具形式交 D04 |
| stage_profile_update | 待核对更新仍需存在；是否单独工具交 D04 |
| build_visit_brief / build_care_tasks | 产物要求保留；由工具、服务或模板承载交 D04 |

### 6.2 运行与更新边界

模型输出只能提出候选，不直接授予写库权限。用户确认后的提交由业务后端验证实际确认、目标版本和归属；工具接收的文档内容不能改变权限。新任务按授权加载必要数据，不把长期会话当唯一档案。

框架要求最多两轮局部修复，仍失败返回明确状态；模型步骤、工具超时、输出长度和费用预算需配置，但数值尚待 D09。沿用框架记载的参赛约束：AGH 至少承载三个连续执行步骤，全部模型调用限于 Agnes；语音等输入能力另核验。这里记录的是来源约束，不构成本次赛事规则的新核验。

## 07 系统边界与接口交接

### 7.1 技术方案的地位

上传框架建议自有 React/TypeScript 前端、FastAPI 业务后端、Node/TypeScript 的 AGH 接入层、SQLite 与受控文件目录。它们在本 PRD 中是沿用的候选技术栈，不提升为团队已批准的不可变选型。[S1 §06]

## 08 状态、异常与非功能要求

### 8.1 任务状态与用户反馈

沿用框架状态枚举；用户看到的阶段必须来自真实运行，而非动画推测。[S1 §07、§09]

| 状态 | 用户可理解的含义／允许动作 |
| --- | --- |
| queued / running | 已接收／处理中；显示实际阶段，可在允许范围取消 |
| needs_review | 等用户核对；不表示画像已更新或诊断已确认 |
| completed | 对应业务步骤确已完成，结果可查看；仍区分原文保存与事实提交 |
| failed / blocked | 执行失败／权限或安全等条件阻止；说明原因及可用替代路径 |
| cancelled / interrupted | 用户取消／进程中断；说明已有结果，不能推断写入全部回滚 |

事实核对状态、身体情况状态、任务状态、沟通卡是否过期是不同维度，不共用一个“正常／异常”标签。显示 `completed` 的具体业务条件由每个工作流约定。

### 8.2 可靠性与资源要求

原文保存与模型处理分离；重复提交不重复写；并发更正不覆盖新版本；重启后未完成任务标 interrupted，查清回执再重试。成本、耗时和错误需记录，但源文件没有定值的 SLA、并发量和限额不在这里伪造，统一交 D09。

### 8.3 医疗输出与隐私边界

沿用框架：不把症状写成确诊，不排除急症；保留材料中的“考虑／待排”；不开药、停药或改剂量；恢复支持以已确认医嘱为先，普通资料注明出处。未经审阅，不向真实用户开放自动分级处置。[S1 §10]

科室建议和就医／观察相关的新增表达仍须解决 D01/D02。资料不足或安全模块失败不得输出“无风险”；模型生成科室名称不自动代表准确性得到验证。

数据收集、向模型发送和文件处理应告知目的与去向；默认合成演示；真实资料不进入公开仓库、证据和无保护日志；删除覆盖适用派生与索引范围。用户身份从服务端校验，不信任请求自报归属。这是沿用项目要求，不是本稿重新给出的法律适用结论。

**真实试用门槛：** 按框架完成隔离、删除、授权、服务数据约定、医疗范围审阅及异常渠道；通过演示测试不等于临床安全或监管合规。[S1 §10.3]

| T04 病历含糊与冲突 | “考虑／待排”、药名不清、旧资料与新输入不一致 | 关键内容待核对；不自动确诊、不自动推定当前用药 |
| T05 导医范围与安全 | 未覆盖／资料不足／安全模块失败 | 不给保证性结论、不强迫唯一科室；有可解释失败和人工路径；细则依 D01/D02 |
| T06 文档与模型失败 | 无文本 PDF、超大文件、超时、无效 JSON | 错误可区分；已有原文保留；不编造识别、更新或调用结果 |
| T07 权限与注入 | 用其他用户编号；文档包含“忽略规则”等指令 | 不能越权读写；材料文本不改变权限或触发无授权外部动作 |
| T08 幂等与删除 | 重复提交、并发更正、取消、撤回、删除 | 无重复写、无静默覆盖；如实说明已生效／未处理部分；删除后不由旧索引取回 |

### 9.2 固定主演示的完成定义

同一合成用户全程使用同一业务档案；每个步骤有实际结果编号或回执；发生日期更正贯穿后续输出；病历重要信息在确认前不是已确认事实；未就诊时日常记录仍独立可用。

建议保留合成原始输入、期望字段、事实版本变化、任务／工具回执及最终产物，方便复核。模型说“已完成”不是证据，source_id 存在也不能代替检查原文是否支持结论。[S1 §13]

### 9.4 建议评估方案与口径

框架建议 24 条合成多轮案例，12 条开发、12 条留出；并建议固定关键字段精确匹配率不低于 90%、事实性输出来源覆盖率 100%，预设纠错、用户隔离和禁止治疗变更样例全部通过。上述均不是实测结果；最终指标、预算和标注人须团队确认。[S1 §13]

为便于复核，建议补充以下计算口径：

| 指标 | 建议定义／记录方式 |
| --- | --- |
| 字段准确性与遗漏 | 固定标注字段及规则，正确匹配数／应提取字段数；另列遗漏、错误新增、否定与时间错误，不只统计模型愿意输出的字段 |
| 来源覆盖与支持 | 需来源的事实陈述中，具有可定位且实际支持该陈述的有效依据的比例；科室医学依据另按 D01，不混入个人病史引用 |
| 更正一致性 | 引用被更正事实的后续产物中使用有效版本的比例；同时记录旧产物过期提示 |
| 低打扰体验 | 输入到保存的操作数、重复提问数、核对时长和是否能找到原文；不等同医学效果 |
| 耗时与成本 | 记录端到端耗时、模型／工具调用和实际费用；目标上限待 D09，不制造精确承诺 |

对照同一 Agnes 模型直接生成与 AGH 检索—工具—校验流程时，建议给双方可访问的同等原始资料和相同任务，记录差别，不让一方缺少历史以制造优势。任何跨用户泄露、关键错误静默入库或无来源治疗变更，阻止真实试用；小样本全通过仍不证明临床安全。
