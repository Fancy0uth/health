2. `healththread_retrieve_context`

Admission and exact resulting registry still need an executable check. ## Scope binding and receipts

Before session.new, the product server reserves an unguessable session key and durably binds it to run ID, authenticated owner, permitted workflow/tool subset, allowed source IDs, consent version, deletion epoch, profile revision and expiry. Keys are server-generated; model args contain no owner, token, path or URL. New W3 continuation gets a new run/key bound only to confirmed instruction versions.

The plugin sends the **Host** ctx.session.key/toolUseId plus validated args to a fixed loopback/Unix-socket business endpoint using a server-owned credential. The endpoint must authenticate the plugin connection as well as check the key; a key supplied by an arbitrary local caller is not authority. Never put the connection credential in plugin tool schemas, result text, prompt, browser config or logs. Recheck scope inside each domain transaction, particularly immediately before any stage write.

Read tools: readOnly=true, destructive=false, replay=safe. Stage tools: readOnly=false, destructive=false, concurrencySafe=false unless transactionally proved, replay=idempotent, requiresApproval chosen explicitly. Set isOpenWorld=false, deferLoading=false, costHint=undefined. Both stages preserve operation_key request-hash semantics; their server transactions produce receipt IDs. Do not set readOnly=true just to avoid taint-based approval: Core asks on tainted non-read-only calls even when requiresApproval is never (`tools.ts:383–385`). If legitimate stage calls ask, approve only a verified known healththread stage invocation with active scope, never every request; deny all other approvals including unknown-outcome repair parking.

Store tool invocation receipt + args hash + sessionKey/toolUseId in the backend, then correlate the actual `tool/call` and `tool/result` ledger seq and structured receipt using `events` or readToolDetail. `tool_result` transform hooks are fail-open and can change the displayed result: the backend receipt remains authoritative. Do not authorize business writes from a model JSON claim or an arbitrary event emitted by a plugin. Completion requires recorded W1 read_source→retrieve_context→stage_candidates (and corresponding W2/W3 sequences), not merely assistant text and lastSeq. Encrypt/access-control retained health-bearing Harness ledgers; sanitized operational logs are separate from model traces. Deletion must honestly account for both.
