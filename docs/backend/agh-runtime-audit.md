## Scope binding and receipts

Before session.new, the product server reserves an unguessable session key and durably binds it to run ID, authenticated owner, permitted workflow/tool subset, allowed source IDs, consent version, deletion epoch, profile revision and expiry. Keys are server-generated; model args contain no owner, token, path or URL. New W3 continuation gets a new run/key bound only to confirmed instruction versions.

The plugin sends the **Host** ctx.session.key/toolUseId plus validated args to a fixed loopback/Unix-socket business endpoint using a server-owned credential. The endpoint must authenticate the plugin connection as well as check the key; a key supplied by an arbitrary local caller is not authority. Never put the connection credential in plugin tool schemas, result text, prompt, browser config or logs. Recheck scope inside each domain transaction, particularly immediately before any stage write.

Read tools: readOnly=true, destructive=false, replay=safe. Stage tools: readOnly=false, destructive=false, concurrencySafe=false unless transactionally proved, replay=idempotent, requiresApproval chosen explicitly. Set isOpenWorld=false, deferLoading=false, costHint=undefined. Both stages preserve operation_key request-hash semantics; their server transactions produce receipt IDs. Do not set readOnly=true just to avoid taint-based approval: Core asks on tainted non-read-only calls even when requiresApproval is never (`tools.ts:383–385`). If legitimate stage calls ask, approve only a verified known healththread stage invocation with active scope, never every request; deny all other approvals including unknown-outcome repair parking.

Store tool invocation receipt + args hash + sessionKey/toolUseId in the backend, then correlate the actual `tool/call` and `tool/result` ledger seq and structured receipt using `events` or readToolDetail. `tool_result` transform hooks are fail-open and can change the displayed result: the backend receipt remains authoritative. Do not authorize business writes from a model JSON claim or an arbitrary event emitted by a plugin. Completion requires recorded W1 read_source→retrieve_context→stage_candidates (and corresponding W2/W3 sequences), not merely assistant text and lastSeq. ## Follow-up: prefer public in-process SDK endpoint over a full daemon

**This supersedes the daemon/worker recommendation above for Task 2.** A constrained `createHost` → `createLocalEndpoint` → `createClient({transport:{kind:'inproc',endpoint}})` composition is a public, production-used path. It eliminates supervisor/socket ownership, worker resource bootstrap and global daemon dependency while retaining actual Harness execution and SDK receipts. The source explicitly describes inproc as the default TUI/print path (`packages/sdk/src/transport/inproc.ts:1–9`), and the real CLI constructs it in `packages/cli/src/boot/local.ts:245–369`. ### Exact endpoint/SDK contract and limits

- Public package subpath: `@agnes/daemon/local` (`packages/daemon/package.json:10`). `createLocalEndpoint(host:Host,opts:LocalEndpointOptions={}):LocalEndpoint & {prompter:Prompter}` at `packages/daemon/src/local/index.ts:323`. It is not a test-only adapter and is not a mock provider.
- `createPrompterBridge():{prompter:Prompter;bind(target:Prompter):void}` is exported from the same subpath (`index.ts:313`). Supply bridge.prompter to createHost, then bind endpoint.prompter after endpoint creation; this is required for SDK permission callbacks to receive real asks.
- SDK inproc endpoint is structural: `handle(msg):Promise<JsonRpcMessage|void>`, `notifications:AsyncIterable<JsonRpcMessage>`, `close():Promise<void>`. There is one server-to-client notification consumer per endpoint. Create one SDK client per endpoint, not several clients racing the same iterator.
- `createClient({transport:{kind:'inproc',endpoint},auth:{kind:'local'},journal:memoryJournal(),timeouts:{request:… ,initialize:…}})` is valid. Correct timeout option is **timeouts**, not requestTimeoutMs. Keep this object private to the backend.
- Session/new/prompt/cancel/set_mode are registered in `local/methods/acp.ts:476,582,676,690`; setPreset/setModel, events attach/detach, projectUI/history/patch, readToolDetail, submit/followUp/steer are registered in `local/methods/agnes.ts:812–1293,1761–1784`. - Package admin and resource-control services are opt-in (`local/index.ts:461–477`). Omit `packageAdmin`, `resources`, `jobs`, `directory`, and artifact/media ports unless needed; no daemon helper packages are installed by createLocalEndpoint. Extensions service RPC exists but has no service to invoke if the approved plugin only supplies tools/hooks. Never expose this endpoint as a generic browser RPC relay.
- Configuration RPC is registered but denies when `opts.configuration` is absent (`local/methods/config.ts:24–38`). Prefer reading configuration directly in the trusted launcher and omitting it from the endpoint. Passing the existing configuration service directly would also make config.save/account/oauth available to the local client; it is unnecessary for the product run path. If AgnesAgent expects config.get, inject a server-side verified snapshot into the adapter or use an explicitly read-only service facade that rejects mutations/tests; do not hand out the writable original service.
- Inproc client.close closes the endpoint and its sessions (`transport/inproc.ts:48–59`, `local/index.ts:493–505`) but does not close the Host itself. If sharing a Host+endpoint+client across runs, keep the client for backend lifetime and create a fresh SDK session per run. On shutdown revoke/cancel/drain, close client, then host.close. A per-run Host/endpoint is simpler but adds assembly cost. Memory endpoint ownership/command journals are valid only for a no-resume lifecycle; the domain store must mark running runs interrupted after restart. Use public durable ownership/workspace indexes if later session/load is required.
