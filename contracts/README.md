# HealthThread API v1

Authoritative HTTP operations: `openapi.yaml` (JSON serialization, valid YAML 1.2). Tool argument schemas: `schemas/healththread_*.json`. Node 24.10+ and SQLite required. `source-validation.mjs` enforces semantic/extractive constraints in addition to structural schemas.

## Identity and requests

Default startup provisions no account. For local synthetic use only, explicitly set `HEALTHTHREAD_DEMO_AUTH=1`, `HEALTHTHREAD_DEMO_USERNAME`, `HEALTHTHREAD_DEMO_PASSWORD` (minimum 10 characters). Existing provisioned accounts persist in the domain DB. Passwords use salted scrypt; sessions are random, server-side and expire in 8 hours. Cookies: HttpOnly, SameSite=Strict, Secure when TLS terminates at this server. Deploy same origin; this service does not trust forwarded host/proto headers.

Every mutation requires exact `Origin`; all except login require `X-CSRF-Token` from `/api/me` or login. Acceptance, confirmation/rejection, correction/retraction, retry and delete require `Idempotency-Key` (16–128 characters). Same operation/key with a different request hash returns 409. Owner fields never determine identity. All object reads use session owner, including results/operations/deletion jobs. Model tools never accept user credentials or owner IDs.

Errors: `{error:{code,message,request_id,phase,retryable,details?}}`. 202 means original data/outbox committed, not model success. `/api/runs/:id` includes `saved_receipt`, status/phase/error, `fact_change_id`, `result_id` (`result_ref` alias), and server `tool_receipts` IDs. `/api/operations/:id` reads acceptance, commit or deletion receipt. JSON bodies only except one PDF `file` multipart part. HEAD is supported for static resources, not API projections.

## Frozen agent interface

`new DomainStore({dbPath,demoAccounts?,clock?,limits?})`; all domain operations take a trusted user ID as their first argument. HTTP server resolves it exclusively from session. Internal `toolsFor(runId)` returns five closure-bound synchronous functions (safe to `await`):

- `healththread_read_source({source_id})` → `{source,sentence_spans,receipt}`.
- `healththread_retrieve_context({query?,episode_id?,source_ids?})` → `{facts,sources,source_spans,conflicts,snapshot_revision,receipt}`. A nonempty query filters normalized literal keywords; source_ids filters fact evidence and episode_id filters assigned episode. Empty filters return the bounded authorized profile. No semantic/vector search or automatic episode merging.
- `healththread_stage_candidates({candidates,base_profile_revision,operation_key,record_dialogue?,record_source_refs?,document_source_refs?,comparisons?,overview?})` → `{fact_change_id,status:'needs_review',receipt}`. New proposals only; correction/retraction starts at the authenticated user endpoint.
- `healththread_get_confirmed_instructions({document_id})` → `{instructions,receipt}`; only for a care-plan continuation bound to that document.
- `healththread_stage_result({kind:'visit_preparation'|'care_plan'|'assistant_reply',payload,dependencies,operation_key})` → `{result_id,status:'completed',receipt}`. Stage performs all validation and persists actual result/tasks.

All tool receipts include server-generated `id`, `operation_id`, `run_id`, `snapshot_revision`, `validation:'passed'`. Every invocation rechecks current owner/source ownership, consent version, epoch, scope generation, expiration and run status. Stage validation and effect/receipt use the same short SQLite transaction. Stage receipts replay at the saved checkpoint; changed payload conflicts. Replaying after cancellation/revocation/deletion fails.

W1/W3 extraction and W2 must read the source and retrieve context before staging. Evidence can only cite actually read sources; fact dependencies can only cite facts actually retrieved in this run. W3 continuation must get confirmed instructions before staging tasks. `source.text_version=1`, UTF-16 `[start,end)` offsets, `locator.page=null` for pasted text or 1-based PDF page. Extracted PDF page records give global text start/end.

`new DispatchQueue(store,agent,{limits?,onDiagnostic?})`; `kick()`, `drain()`, `cancel(runId)`, `status()`, `resume()`, `close()`. Agent must identify `mode:'fixture'|'real'` and implement `run({run,scope,tools,signal})`; optional `isReady({signal})` shares the deadline. It must invoke bound tools, not return invented output for the queue to save. Scope argument contains IDs/allowed sources/snapshot/consent/expiry for trusted adapter wiring, never a model-authorizable owner.

Fixture return does not certify real execution. Real adapter return must be `{agh:{provider:'agnes-ai',model,session_id,last_seq,tool_receipt_ids}}`; IDs in exact order must equal actual persisted tool receipts. Adapter must derive session/seq/provider from SDK, never model text, and cap output repair at two attempts. This backend cannot prove SDK provenance by itself; the trusted adapter owns that boundary. A provider failure after a valid checkpoint preserves staged effects and records `execution_error` with `phase:'after_checkpoint'`; it does not mint real runtime metadata.

## Extractive policy and review

Every candidate evidence quote must equal the rendered value; unrelated auxiliary evidence cannot supply field, assertion, temporal scope or effective time. Candidate value is a verbatim complete source sentence, using period/semicolon/newline boundaries, not a generated medical inference. Preserve uncertainty, negation and temporal markers; conflicting past/current clauses and “not mentioned” reject rather than becoming false certainty. `reported_text` is the safe general field; clinical field types have narrow explicit support marker checks. This is a conservative heuristic, not general semantic proof. All facts still require user review. Unknown times retain source raw text or null; start/end remain null. Exact dates must be real calendar dates present in raw evidence. Relative time is not converted automatically.

W2 `speech` must exactly equal claim texts joined with `\n`. Every cited fact value and source quote must equal the rendered claim text; dependencies are mandatory for each claim. At least one rendered claim must be directly supported by the current concern source. Attaching an unused concern quote to a history claim is rejected. Sources retain their `kind` and review provenance; clients must label source-only claims as unreviewed self-report/document text. Questions must end in `?`/`？`; explicit dosage/action additions are rejected. Department/triage are server-filled `{status:'not_configured'}`. W3 task text must exactly match a confirmed instruction; `instruction_refs` identify revisions; schedule is null or an exact literal substring containing an explicit time marker. No dose/time synthesis. Every referenced instruction must have exactly that task text, and every distinct confirmed document instruction text must appear. Identical instructions may share a task that cites their corresponding fact revisions. Empty tasks are allowed only when none are confirmed, with an explanation. Task status updates require expected_version; stale tasks reject.

A confirmation atomically checks profile revision, all accepted proposal IDs, consent/source/epoch, validates evidence again, appends FactRevisions and audit, updates profile, writes commit receipt and marks existing results/tasks stale. Invalidating all prior derivations on any fact change is deliberately conservative. W3 confirmation additionally creates a distinct queued continuation; it never waits for a model inside the HTTP transaction. Each new input receives its own pending episode unless the user explicitly selects an existing owned episode; no keyword merging.

## Recovery and limits

Queued → running → needs_review (W1/W3) or completed (W2/continuation). User confirmation/rejection ends needs_review; W3 optionally queues continuation. queued/running/needs_review can cancel. On startup running → interrupted, queued remains dispatchable, needs_review persists. failed/blocked/interrupted can create a new run through `/retry`; original remains historical and no source is duplicated. cancelled/completed/needs_review cannot retry. A needs_review checkpoint can instead POST `/api/runs/:id/reanalyse` with `{expected_profile_revision}` and a fresh Idempotency-Key. It checks the current profile, owner/consent/sources, then atomically expires the old proposal, revokes its scope and creates a new referenced run/outbox using the same saved sources. Receipt includes `run_id`, `source_id`, `operation_id`, `expired_fact_change_id`, `saved:true`. It never copies stale proposals into current facts. Explicit `/api/fact-changes/:id/reject` uses the current expected profile revision without requiring the old proposal base to match; rejection changes no facts. GET review now returns `review_revision`, the current profile revision captured by the review page. Confirmation submitted with an old captured revision remains409; freshly reopening an unchanged extractive draft may confirm it at the current revision, even when its generation base is older. Evidence/source/consent/epoch and referenced fact versions are always revalidated. Clients must not silently update a pending confirmation operation. Missing model yields blocked after source preservation. Provider errors never become empty successful output.

Scheduler storage errors are contained at the claim and task-rejection boundaries. Durable queued records remain untouched on failed claim. Defaults allow 3 automatic attempts, exponential backoff starting at 250 ms capped at 5000 ms, then suspended until an explicit in-process operator `jobs.resume()` or service restart. `/api/health` remains live and exposes `dispatch.state`, failure count, next-attempt timestamp and sanitized `last_error`. Diagnostics include correlation IDs/code/phase, never SQLite messages or source text. Unknown in-flight effects are interrupted (or preserved checkpoints receive execution_error) on recovery, never automatically replayed.

Defaults: text 100000 bytes; PDF original 5000000 bytes; PDF 30 pages / extracted text 150000 bytes; JSON body 7000000 bytes; queue 100 global / 10 per user; concurrent runs 2 global / 1 per user; runtime deadline 300000 ms from dispatch, including readiness; separate queue expiry 600000 ms; absolute tool scope 900000 ms; output 150000 bytes; retrieve 100 records; login 10 attempts per remote address per 15 minutes. PDF extraction uses fixed `pdfinfo`/`pdftotext` executable paths, argument arrays, 15-second hard subprocess timeout, output bound and private random temporary directory; requires local Poppler. No OCR. Text over the normal source byte limit remains rejected before acceptance, even if within PDF extraction limit.

`QUEUE_BUSY` (429) is rejected before saving. Auth 401; CSRF/consent/scope 403; foreign/missing IDs 404; state PUT 405; stale version/idempotency 409; replay of erased source 410; byte/page limits 413; unsupported media 415; invalid evidence/PDF 422; missing extraction dependency 503. Original-PDF rejection before extraction/acceptance does not report it saved.

## Storage and erasure

Live default DB is `.runtime/healththread-domain.sqlite`. Historical `.runtime/healththread.sqlite` is the anonymous prototype and is never imported or used by active domain APIs; its cleanup is outside current-user domain deletion. SQLite stores bounded original PDF BLOBs in the same acceptance transaction. Source and FactRevision text are immutable by DB trigger; corrections append revisions.

Deletion removes matching local source/entry/document/episode/revisions/candidate/result/task text and PDF BLOBs, invalidates scopes, preserves minimal opaque operation/run tombstones and request hashes to prevent replay resurrection. Receipts never hold input body text. Response always reports `partial`: active SQLite rows and original BLOBs deleted, AGH trace erasure and external backups/storage remnants unverified. It does not claim secure deletion of filesystem snapshots or the historical prototype DB. `/export` includes only session-owner objects and base64 originals.

## Trusted AGH runtime integration

`reserveRuntime(runId)` creates a private server-selected session key, then `bindRuntimeSession(runId,key,sdkSessionId)` requires exact SDK identity equality. `checkRuntime` rechecks ownership, source set, profile/consent/epoch, expiry, cancellation and scope generation. `toolsFor(runId,{session_key,tool_use_id})` is a trusted adapter-only overload: these values never appear in model arguments or HTTP input. Each successful effect and receipt atomically records the actual session/tool-use IDs and canonical input hash. The adapter correlates these to actual SDK tool/call and tool/result sequences using `readToolDetail` before returning real metadata. Server-derived W2 department/triage fields are added to a copied payload, preserving input hashes.

`recordRuntimeRepair` persists the shared maximum of two local repairs, including Core pre-execution argument rejects and outer missing-stage prompts. A valid checkpoint whose original SDK turn was blocked after one repaired tool error can use the remaining repair for a plain acknowledgment turn; a private finalization flag rejects every tool effect during it. Both actual turn reasons/stop reasons/sequences remain evidence. Failure still retains the checkpoint with `execution_error`. Runtime binding/evidence is private and excluded from HTTP/export; source deletion removes matching private bindings, with AGH trace erasure still unverified.

`sentence_spans` is additive immutable-source evidence, each already shaped as `{source_id,source_text_version,locator:{page,start,end},quote}`. It mechanically preserves complete literal sentence spans, UTF-16 positions, punctuation and original line breaks; it does not classify or confirm health claims. Whitespace-only CRLF separators are skipped without changing source text. PDF spans must fit entirely inside one actual page. More than 100 spans, over 32768 quote bytes, or a sentence crossing page bounds fails closed. Source-only material remains unconfirmed. Actual domain-validator errors include bounded field/path/rule feedback for locator, full-sentence, assertion, temporal and new-proposal identity failures.

## Cross-device run discovery and erasure epochs

Authenticated `GET /api/runs?limit=50&before=<next_cursor>&source_id=<id>&status=blocked` returns `{runs,next_cursor}`. `GET /api/documents?limit=50&before=<next_cursor>` returns `{documents,next_cursor}`. Both are newest-first, default50/max100, use opaque stable keyset cursors, exclude deleted records and derive owner only from the session. Unknown/duplicate/invalid query values return400; a foreign/missing source filter returns404. Run rows and single-run GET use the same sanitized public projection plus saved_receipt; owner, scope authority, read sets, expiry/deadline and private runtime bindings are omitted. No full-source body is in discovery responses; use the authorized source endpoint. OpenAPI defines RunSummary/DocumentSummary and typed page schemas.

`/api/me` and login now include integer `scope_epoch` and `all_clear_epoch` (null for signed-out me). Successful authenticated responses publish fresh `X-HealthThread-Epoch` and `X-HealthThread-All-Clear-Epoch` headers after mutation. All authenticated business mutations except logout require `X-HealthThread-Epoch`: positive safe integer from the immutable operation ticket. Missing/invalid is428 EPOCH_REQUIRED; a stale uncommitted mutation is409 SCOPE_EPOCH_CONFLICT. This is optimistic concurrency, never owner authentication. Capture before dispatch, do not silently upgrade a pending operation's header after deletion/revocation.

HTTP passes the expected epoch into the actual domain transaction, including after asynchronous JSON/PDF reading and extraction. Direct trusted in-process callers may omit the final expectedEpoch argument; HTTP cannot. For idempotent methods, matching immutable receipt lookup precedes the epoch guard so a committed same-key deletion can recover a lost response without deleting again or incrementing any counter. Changed bodies still conflict; a prior acceptance whose source was erased still returns410 SOURCE_DELETED. An old request without a committed receipt cannot recreate a source under the new epoch.

The existing users.epoch is the public scope_epoch, advancing on consent changes and source/all deletion. New users.all_clear_epoch starts0 and increments only for a new all-data deletion, including when no sources exist. Single-source deletion and consent revocation invalidate pending operations without demanding deletion of unrelated local drafts. Clients observing all_clear_epoch change clear all local health drafts/journals, even on another device without BroadcastChannel or with previously empty source lists. Existing databases migrate this counter with default0 while preserving the prior scope epoch. The counter is durable; it is not a session credential.

## Original-page assistant and login

`POST /api/health-assistant` is now a dedicated `chat` workflow, accepting `question` and optional owned `selected_source_ids`; it no longer aliases visit preparation. Acceptance receipts and run summaries expose the server-assigned `conversation_id`. The first selected earlier chat run determines the same owner's conversation; browser-supplied conversation identities are not trusted. Original clients keep at most six preceding question sources per new turn. An `assistant_reply` uses the visit stage's exact source/fact claims and question restrictions, plus a bounded intent enum. Interface framing is deterministic; model-generated questions and source quotes come from the stored result. Chat never stages facts/cards/tasks. Native pages rebuild canonical question/reply history from backend sources/results.

Original-page operation subscribers receive an operation on every operation event, including before POST. A lost response retains its original idempotency key for explicit recovery. Native real-mode waiting continues after staging until runtime correlation metadata or an explicit execution error arrives; a staged result alone does not display a verified AGH badge. Both platforms show the current account and support logout; same-origin cookies share the authenticated session.

## Record dialogue (W1)

`POST /api/record-turns` accepts a new `{text}` or a follow-up `{text,record_thread_id,expected_version}`. `existing_source_id` converts an owned visit-only context into a record without duplicating its original; an existing record source cannot be wrapped twice. Ownership, epoch, consent, thread version, finite aggregate size and queue admission are checked in the same transaction as immutable source/entry/thread/run/outbox persistence. Follow-up expires the previous pending proposal. Retry and reanalysis retain the thread, reference its latest run and reuse original sources.

W1 record dialogue runs require `record_dialogue:{questions,missing_fields}` in `stage_candidates`, covering all read turns. The summary stores immutable source/candidate IDs, metadata, missing-field labels and at most three model questions. `/api/state.state.recordThreads` reconstructs both original frontends' conversation histories. User input remains source text; formatting does not extract additional medical facts.

Typed replies use the normal confirm endpoint with `{accepted_change_ids,expected_profile_revision,record_summary_id,confirmation_message}`. Only explicit literal confirmation phrases are accepted, bound to the latest owned summary and its full candidate set. Reply/commit acknowledgment and formal facts are atomic; confirmation text is not a health source and is not sent for inference. Timeline confirmation may select a subset, records its selected IDs and updates the thread. Unknown acknowledgments recover the exact original operation/key; no new submission or profile-version upgrade. Source deletion withdraws dependent thread/summaries/confirmations; all-data deletion clears them. Export has typed `record_threads`, `record_summaries`, `record_confirmations` arrays.

## Health profile and post-visit continuity

Candidates in both supported input paths may include optional `health_observations`: `[{dimension,value,unit?,observed_at?}]`. In the natural path this property belongs to each `record_source_refs` item; manual candidates carry it directly. Dimensions are `body_site|symptom|onset|course|self_rating|impact|context|associated|measurement|background`. Each candidate permits at most 50 observations. `value` is a nonempty exact supported snippet (maximum 2000 characters); unit and observed time are optional/nullable exact source snippets (100/200 characters). Preserve negation and uncertainty; never infer a score, unit, date, diagnosis or event time from the recording time. Complete sentence evidence stays unchanged. These fields remain optional for legacy callers and data; backend semantic validation is stricter than JSON shape validation.

`healththread_stage_candidates` also accepts optional `comparisons` (at most 100): `[{candidate_index,fact_id,revision,relation,reason}]`. The index is zero-based in the original `candidates` or `record_source_refs` array; invalid/unsupported selected sentences cannot shift another comparison to a different candidate. References must identify readable, currently confirmed same-owner facts actually retrieved in the run. Relations are `conflict|update|duplicate|related`, with a nonempty reason of at most 2000 characters. Explicit temporal change is an update, not a simultaneous contradiction. The server attaches old/new snapshots and may surface conservative possible conflicts even when the model omitted them. Neither model comparisons nor extraction automatically replace facts.

`GET /api/profile` preserves `facts` and `pending_changes` and adds `health_profile`: observations with version/provenance/review state, current problems, events, background, unknowns and conflicts. `PATCH /api/episodes/:id` accepts `{status:active|improved|resolved,expected_version}` and changes separate current event state while preserving the historical episode. A status such as resolved is a patient report, not a diagnosis.

Review confirmation optionally accepts `resolutions:[{candidate_id,fact_id,revision,action}]`. `replace` updates only the selected old fact using version checks and retains history; `keep_both` retains distinct records; `keep_existing` adds no new fact; `defer` leaves uncertainty reviewable. Selected conflicts require explicit resolution. Unselected conflicting candidates must remain pending or explicitly deferred and cannot become confirmed as a side effect of partial review. Current owner, evidence, consent, epoch and fact versions are rechecked at confirmation.

Each care task may add `explanation` (nonempty, at most 4000 characters) and `questions` (at most 10 nonempty strings of at most 1000 characters). These are model paraphrase and clarification metadata displayed separately from the exact original `text`, `instruction_refs` and `schedule`. Explanation must remain faithful to those confirmed instructions, preserving dose, frequency, timing, conditions and uncertainty; no unsupported quantity, new action or medication change is allowed. Unknown medicine, dose or timing becomes a question, never a guessed instruction. Older tasks without these fields retain the original instruction without inventing an explanation.

`POST /api/care-tasks/:id/feedback` accepts `{text,expected_version}` with idempotency, consent, ownership, CSRF and epoch checks. It atomically saves an immutable patient self-report linked to the task and instruction revisions and creates a chat run; its receipt includes the saved source, run and conversation identifiers. Feedback does not automatically confirm health facts or edit the instruction. Feedback on stale tasks keeps explicit historical provenance without reviving the task. Export and dependent deletion include observations, comparisons, event state and feedback along with the existing history.

### Bounded document and legacy-record reliability

Document staging prefers `document_source_refs:[{source_id,sentence_index,field,health_observations?}]` with `candidates:[]` and a native `overview` object. References must be actually read/authorized; exact evidence and literal annotations are reconstructed before the existing clinical source validation. Duplicate, out-of-range and mixed inputs reject atomically. Comparison indexes refer to the original compact input order. Unsupported/ambiguous sentences remain immutable source text and narrative uncertainty, never inferred clinical facts. Complete legacy candidates remain supported.

Explicit `POST /api/runs/:id/reanalyse` additionally adopts standalone self-report entry records, including completed/confirmed legacy records, into one editable thread on their existing episode. Documents and unrelated workflow runs do not gain this eligibility. Receipt adds `record_thread_id`/`record_version`; `expired_fact_change_id` is null when confirmed history is retained. Retry preserves the linkage and automatic-overview requirement.

Whole-record edits require overview before staging and finalization. The saved current record narrative is exactly the submitted source text; the model synthesis is separate. Prior same-episode facts are excluded from current retrieval and old sources are marked history; new edit facts may cite only the authoritative edit source. Reanalysis preserves record_edit. Original sources and confirmed history remain unchanged until a valid replacement is verified.
